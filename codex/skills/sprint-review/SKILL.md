# Sprint review

Read original requirements, selected plan or tracker scope, relevant diffs,
and verification evidence. An explicit selection needs no second confirmation.
If no sprint document exists, review the tracker or supplied list without
requiring a new folder.

For each promised outcome, determine delivered, failed, unverified, or pending
human acceptance. Check for requirements omitted from the task breakdown. Reuse
valid gate records; rerun only checks invalidated by changes or missing evidence.
A closed issue alone is not acceptance evidence.

Present one outcome/evidence table. Ask the user only about requirements that
reserve their judgment, disputed behavior, or proposed scope changes. Do not
demand an accept/reject conversation for every routine task. Required human
verdicts remain open until received.

Apply tracker updates covered by the review request through `itr` or the existing
tracker. Reuse open items for carryover. File new follow-ups only when authorized
and after duplicate checks. Do not turn every observation into another ticket.

Record a short lesson only when a real failure, intervention, or repeated cost
suggests a concrete change. No automatic retrospective interview, process-task
quota, or extra retro file. Update existing Outcomes/Review sections and preserve
unrelated content and history.

Close an epic only when required outcomes are verified and accepted, or the user
approves a changed scope with carryover recorded. A percentage threshold does
not override a missing goal-critical requirement. Update or clear `sprint/CURRENT`
only when it refers to this sprint and the sprint has actually closed.

Report delivered results, checks, remaining IDs, required verdicts, and concrete
next actions. Do not start the next sprint, commit, or push merely to close review.
