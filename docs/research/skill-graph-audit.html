Skill Graph Audit

Graph engineering treats an agent system as a graph. Nodes do the work (an agent, a script, a person), edges decide what runs next, and state is what the nodes pass along. This page reads every orchestration skill in the repo that way: which techniques each one uses, where the graph is held, and which graphs are missing.

The topologies are all here

The dojo rack alone names twelve distinct cuts, and the larger skills combine them. Nothing in the standard pattern list is absent.

The edges are mostly prose

One skill, crucible, ships its stage graph as a script. Three more put a script on the edge that matters most. Everywhere else the orchestrating model reads the next step from SKILL.md.

The work graphs are recorded, then read by eye

Dependencies and file ownership are written down, but waves and ordering are worked out by the model. itr graph, itr ready and kgr impact are called by no orchestration skill.

The yardstick

The sources agree on the parts even where they disagree on whether the name is new. These six are what the rest of the page checks for.

Typed nodes

Deterministic code, a single model call, a tool, a full agent with its own loop, or a person. Each has a contract: inputs, outputs, allowed tools, retry policy.

Explicit edges

Direct, conditional, parallel, loop, error, human-controlled and event-triggered. Hard constraints route in code and are not left inside a prompt.

Scoped state

Typed, and each node reads only what it needs and writes only what it owns. Checkpoints make pause, resume and replay possible.

Named topologies

Chaining, routing, fan-out and fan-in, orchestrator and workers, evaluator and optimizer, voting, DAG scheduling.

Reliability on the graph

Validation gates, bounded loops, error classes, a judge that is not the writer, a trace per node, and evaluation of the structure itself.

Graphs as data

Dependency, capability and code graphs that the workflow reads. They are a different thing from the workflow graph and feed its routing.

What is missing, in order of return

Every item moves a rule the skills already state into something computed or checked. None adds a new skill. Sizes are rough: S is an afternoon, M a few days, L a week or more with a proving run.

Start here

  1. Compute the waves M

    Today
    blitz, crossfire-blitz and proof-campaign build conflict-free waves by having the orchestrator read file lists and blocked-by fields and pack them. blitz says outright that an incomplete file map cannot be caught before fan-out.
    Add
    A waves mode beside preflight.sh, where preflight facts already have one home. It takes itr graph and the declared files, widens each file set with kgr query --who-imports, and prints the waves as key: value lines.
    Return
    The same plan on every run, a plan a resumed run can re-read, and fewer mid-wave collisions. This is the busiest graph in the repo and the one with the most model effort spent on arithmetic.

  2. Seat the judge on another model in the dojo and forge-change S

    Today
    crossfire-blitz, crucible, gauntlet, council and feature-build --strict all put the reviewer on a different model. shadow-duel, whetstone, hundred-blades --judge and forge-change's challengers set no model, so the critic runs on whatever wrote the work. drawn-steel is described on the rack as "cheapest model first" but its rungs raise effort only.
    Add
    One line in each file: critic, challenger and judge seats resolve the reviewer role at spawn time, and drawn-steel's rungs follow the MODELS.md ladder.
    Return
    The survey's first listed anti-pattern is the same agent writing and judging its own output. These are the four places it still happens.

  3. Give the dojo a bar that a command decides S

    Today
    No blade runs a command or reads an exit code. first-blood trusts a runner's "Cleared: YES", drawn-steel says to verify against the bar yourself, and shuriken-storm's landed is a self-reported boolean.
    Add
    An optional --bar-cmd that the orchestrator runs through gatr. The exit code picks the edge: deliver, next rung, next round, or miss.
    Return
    The evaluator writes state and code picks the edge, which is the pattern crucible already proves with gate.mjs.
Next

  1. One run-state file for the prose graphs M

    Today
    The dojo, forge-change, feature-build and council hold the plan and every return in the orchestrator's context. blitz writes a wave log but has no resume procedure. A compaction in the middle of a run loses the position in the graph.
    Add
    Generalize codex-seat's seat directory. A run directory with a small plan.json (nodes, owned files, status) written at the throw and updated on each return, with typed status fields like shuriken-storm's LAND schema.
    Return
    Resume after context loss, and a record that item 5 can read.

  2. Trace per node, where today it is per week M

    Today
    session-metrics.mjs reports per ISO week, and its header says Workflow agent() calls and GPT seats are not counted. crucible, gauntlet and crossfire-blitz each keep a ledger in a different shape. Seat Guard already enrolls every seat at spawn and has a ledger tool.
    Add
    One ledger row format: run, skill, node role, model planned and actual, tokens, outcome.
    Return
    skill-evals could then compare structures: crossfire-blitz with review off, council with one seat, blitz at width 3 against 5. It would report the numbers and leave the call with you.

  3. Make roadmap dependencies real edges M

    Today
    Section dependencies are prose bullets, the cycle check is a walk the model performs, the deps array in queue.json is read by nothing, and the campaign's roadmap update returns as a packet applied by hand.
    Add
    Roadmap stubs are already itr issues keyed by their section token. Record the edges with itr depend, take cycles from itr graph and ordering from itr ready, and have proof-campaign finish by calling /roadmap --update as sprint-review does.
    Return
    Sprint and campaign order come from one graph, and the campaign loop closes.

  4. A Claude-side skill graph with a dangling-reference check S

    Today
    Codex has a registry with cycle detection. On the Claude side the routing graph exists only in description strings and hand-off sentences, and none of the nine validator sections checks their targets. The 2026-10-24 prune archived dozens of names that other skills may still point at.

    A tenth validator section that extracts every /name in a description or body and fails on one that is not an installed skill, a dojo blade or a built-in. Write the edge list out so the explorer can draw it.

Where more graph would cost more than it returns

The repo's own history argues against adding structure for its own sake. Thirteen blades went undrawn, and the one script written for claude/workflows/ was archived without ever running. The sources say the same: LangChain moved its deep-research example from a fixed graph back to an agent harness, and the survey notes that "adding more connections does not necessarily improve collaboration."

So the list above leaves judgment inside the nodes and only hardens edges that are already written as hard rules.

Sources and method

Six reader agents each read one group of files in full and reported with line citations. I spot-checked the claims the gaps rest on: the itr command list, the absence of model settings in the blades and forge-change, the absence of itr graph, itr ready and kgr impact in every skill, and the contents of gauntlet's assets folder.
